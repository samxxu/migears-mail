# P2-5 — `SmtpMailer` writes a caller's custom `Bcc` header verbatim into the …

## Finding

- `SmtpMailer` writes a caller's custom `Bcc` header verbatim into the message, and that one message goes to every recipient — so the address the Bcc exists to hide is delivered to all of them. `withBcc()` is safe: it issues `RCPT TO` for those addresses and writes no header at all. The leak needs the header route, `withHeaders(['Bcc' => …])`, which the README now says is written through like any other custom header. The code neither refuses the combination nor strips the header before the body is sent, and this is the one header whose being written down defeats its purpose.

- Verification: reproduced

  **Where it lives.** The custom-header loop at the end of `buildMessage()` writes a caller's `Bcc` into the message; the envelope is built in `send()` from `array_merge($mail->to, $mail->cc, $mail->bcc)`. A custom `Bcc` address is therefore not a recipient — it is disclosed, in the message headers, to every address the envelope already carries, which is the one thing a Bcc exists to prevent.

  **(A) Refuse, loudly.** Detect a custom `Bcc` (case-insensitively) in `send()` before the transport is opened and throw `MailException`, e.g. *A custom Bcc header is not supported by SmtpMailer; use withBcc()*. About four lines plus two tests. `withBcc()` is untouched — it issues `RCPT TO` for those addresses and writes no header at all — and no message can carry a Bcc line again. No delivery change.

  **(B) Treat the header as the envelope list.** Pull the custom `Bcc` out of the headers, validate each address with the same `filter_var` the rest of this module uses, merge it into the RCPT list deduplicated against `to`/`cc`/`bcc`, and write no header. About fifteen lines plus four tests. This is the "do what the caller meant" answer, it keeps the header route working, and it pays for that with an address path that today is not validated.

  **(C) Strip the header silently.** The caller's addresses receive nothing and nobody is told; against this module's fail-loudly style.

  **(D) Keep documenting it and close this `deferred`.** No code, and the disclosure stays.

  Recommendation: **(A)**, for the reason that decided `P2-4` — `withBcc()` already exists, and this is the one header whose being written down defeats its purpose. (B) is defensible if the header route must keep working, and then it needs the validation.

  Whichever way it goes, the same decision should cover `To` and `Cc` in this driver while you are in there: a custom `Cc` is written into the message while the envelope still uses `withCc()`, so it is displayed but never delivered — the mirror image of `P2-4` — and a custom `To` likewise overrides what is shown while delivery follows `withTo()`. The README's driver paragraphs should end up saying, per header name, whether it feeds the envelope. # P2-5 — `SmtpMailer` 会把调用方自定义的 `Bcc` 头原样写进报文，而这份报文会发给每一个收件人——于是 Bcc …

## 问题

- `SmtpMailer` 会把调用方自定义的 `Bcc` 头原样写进报文，而这份报文会发给每一个收件人——于是 Bcc 本要藏起来的那个地址被投递给了所有人。`withBcc()` 是安全的：它为那些地址发 `RCPT TO`，一个头都不写。造成泄露的是走头这条路径，即 `withHeaders(['Bcc' => …])`，而 README 现在写明自定义 `Bcc` 与其他自定义头一样原样透传。代码既不拒绝这种组合，也不在报文体发出前剥掉该头，而这恰恰是唯一一个「被写下来就失去意义」的头。

- 位置：`src/SmtpMailer.php — the custom-header loop beside the RCPT handling · README.md:129 / :276`
- 验证：已实证

## 讨论串

- 2026-10-01 · `coordinator — cross-module` · `open` — 由协调人立案：由协调人依据模块主 2026-10-01 那次传令中的回报立案，是上面那处残留的对称物：P3-8 已按用户裁定的选项 A 关闭，因此 README 现在写明这个透传行为、而不再否认它，而代码仍会把该头写给所有收件人。协调人按 P2 立案，理由与其姊妹条相同——一个公开入口，其接受的输入会产生调用方预料不到的结果——同样可用 `rejected` 加证据回复。代码该拒绝这种组合还是继续把它写进文档，属行为变更、归用户裁定。

- 2026-10-01 · `coordinator — cross-module` · `new-evidence` — 修复建议，由协调人给出：选项由模块主选，凡会改变投递行为的由用户裁定。

  **它住在哪。** `buildMessage()` 末尾那个自定义头循环会把调用方的 `Bcc` 写进报文；而信封在 `send()` 里由 `array_merge($mail->to, $mail->cc, $mail->bcc)` 拼出。因此自定义 `Bcc` 里的地址并不是收件人——它被写在报文的头部里，通知给了信封上已有的每一个地址，而这恰恰是 Bcc 存在的唯一目的所要防止的事。

  **（A）响亮地拒绝。** 在 `send()` 里、打开传输之前，按大小写不敏感判定出自定义的 `Bcc` 并抛 `MailException`，例如 *自定义 Bcc 头不受 SmtpMailer 支持；请用 withBcc()*。约四行代码加两个用例。`withBcc()` 不受影响——它为这些地址发 `RCPT TO`、一个头都不写——此后也没有任何报文再能带上 Bcc 行。投递行为不变。

  **（B）把该头当作信封名单。** 把自定义 `Bcc` 从头部取出，逐个地址走本模块其余各处用的同一道 `filter_var` 校验，合并进 RCPT 列表（与 `to`/`cc`/`bcc` 去重，避免同一地址收到两次），并且一个头都不写。约十五行代码加四个用例。这是「照调用方的本意办」的答案，头这条路径继续可用，代价是今天多了一条不经校验的地址通道。

  **（C）静默剥掉该头。** 调用方给的地址什么也收不到，而且没人被告知；与本模块「响亮失败」的取向相悖。

  **（D）继续文档化，把本条按 `deferred` 关闭。** 不改代码，泄露照旧。

  建议：**（A）**，理由与 `P2-4` 相同——`withBcc()` 本来就在，而这恰恰是唯一一个「被写下来就失去意义」的头。（B）在意头这条路必须继续可用时也站得住，那就必须补上校验。

  无论选哪条，顺手把本驱动的 `To` 与 `Cc` 一并定下：自定义 `Cc` 会被写进报文，而信封仍用 `withCc()`，于是它只被显示、从不被投递——正是 `P2-4` 的镜像——自定义 `To` 同理，覆盖了显示而投递仍跟着 `withTo()`。README 的驱动段最终应当逐个头名写明它是否进信封。若这件事想单独留个编号，说一声，协调人来立；编号归工具。
