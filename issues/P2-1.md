# P2-1 — Non-ASCII attachment filenames and non-ASCII display names are emitted …

## Finding / 问题

- EN: Non-ASCII attachment filenames and non-ASCII display names are emitted as raw bytes in both drivers: no RFC 2231 filename* continuation for filenames, no RFC 2047 encoding for the From display name. A conforming client shows mojibake, which is what the RFCs exist to prevent.
- 中文: 非 ASCII 的附件名与显示名在两个驱动里都按原字节输出：附件名没有 RFC 2231 的 filename* 续行，From 显示名没有 RFC 2047 编码。合规客户端会显示乱码，而这两份 RFC 正是为此而设。
- Where / 位置: `src/NativeMailer.php:67,79,81,90 and src/SmtpMailer.php:97,153,165,167`
- Verification / 验证: reproduced / 已实证

- 2026-10-01 · `owner — migears-mail` · `fixed` — reproduced, then fixed in both drivers. Before, both drivers emitted the display name and the attachment name as raw UTF-8 — probe showed `From: "张三" <from@example.com>` and `Content-Disposition: attachment; filename="报告.pdf"`, with no `filename*`. Now each driver adds `formatFrom()` (a non-ASCII display name becomes an RFC 2047 encoded-word using `$mail->charset`: `From: =?utf-8?B?5byg5LiJ?= <from@example.com>`) and `mimeParameter()` (a non-ASCII value keeps an ASCII fallback and gains an RFC 2231 companion: `filename="______.pdf"; filename*=utf-8''%E6%8A%A5%E5%91%8A.pdf`, likewise `name*`) — `src/NativeMailer.php:92,136-170`, `src/SmtpMailer.php:97,180-214`, wired at `buildAttachmentPart()` in both. Regression: `NativeMailerTest::testNonAsciiDisplayNameAndAttachmentFilenameAreEncoded` and `SmtpMailerTest::testNonAsciiDisplayNameAndAttachmentFilenameAreEncoded`.
