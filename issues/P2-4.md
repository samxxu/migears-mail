# P2-4 — The native driver appends a caller's custom `To`/`Subject` header …

## Finding

- The native driver appends a caller's custom `To`/`Subject` header beside the real ones `mail()` receives, and nothing reconciles the two: `mail()` is still handed the real recipient and subject while the extra header carries the caller's, so the delivered message can hold two conflicting `To:` headers, and two `Subject:` as well. Routing is unaffected — the envelope comes from `mail()`'s argument — but the message the recipient sees can name an address the sender never meant to show, and can show a doubled or concatenated subject. Triggered by `withTo(...)`/`withSubject(...)` together with `withHeaders(['To' => …])` or `['Subject' => …]`. The SMTP driver overrides cleanly, so the two drivers disagree here, which is what the README now says per driver.

  **A correction to the mechanism this item was filed with, first.** I wrote that routing is unaffected, and that holds only where the MTA does not take recipients from the headers. PHP hands the message to `sendmail_path` — stock value `sendmail -t -i` — and `-t` makes the MTA read recipients out of `To:`/`Cc:`/`Bcc:`, which is why a `To:` line in the fourth argument is the classic recipient-injection vector and why Suhosin ships a level that strips exactly To/Cc/Bcc from additional headers. On a stock Unix setup the second `To:` can therefore add a real recipient, not only a second visible line. Verify against the deployment's own MTA before choosing: a Windows relay, or a `sendmail` invoked without `-t`, may differ.

  **(A) Refuse the combination, loudly.** In `send()`, before `deliver()`, and case-insensitively — header names are case-insensitive and the loop stores them verbatim — throw `MailException` when `$mail->headers` carries `To` or `Subject`, e.g. *Custom To/Subject headers are not supported by NativeMailer; use withTo()/withSubject()*. About five lines plus two tests (`withHeaders(['To' => …])` and `['Subject' => …]` each throw; a third custom header still goes through untouched). No input that is not already contradictory changes behaviour, no mail ever goes somewhere new, and the module keeps one way to name a recipient. README: the native driver refuses them rather than appending them.

  **(B) Honour the header.** Pull `To`/`Subject` out of `$mail->headers` in `send()`, hand them to `deliver()` as `$to`/`$subject`, and skip them in the header loop so exactly one line is written; `Subject` goes through `encodeSubject()`, and a custom `To` through the same `filter_var` validation every other address in this module gets, or the module gains an unvalidated route into the envelope. About ten lines plus four tests. This is what the README promised before this round, and it makes the two drivers agree for these two names — at the price of a real behaviour change: mail addressed by `withTo()` today starts going to the custom header's address instead.

  **(C) Strip the header and keep `mail()`'s arguments.** Two lines, and it silently discards something the caller wrote. Against this module's fail-loudly style; not recommended.

  **(D) Keep the documented boundary and close this `deferred`.** No code. The duplicate line stays, and on a `-t` MTA so does the extra recipient.

  Recommendation: **(A)**. `withTo()` and `withSubject()` already exist, so the header route is a second way to say the same thing; refusing it removes the ambiguity without ever changing where a mail goes. (B) is the better fix only if the project wants the header to win, and then it needs the validation plus a README sentence saying a custom `To` re-targets delivery. Whichever is chosen, the same question has to be answered for the SMTP driver's `To`/`Cc` — see `P2-5`.

# P2-4 — 原生驱动会把调用方自定义的 `To`/`Subject` 头追加在 `mail()` …

## 问题

- 原生驱动会把调用方自定义的 `To`/`Subject` 头追加在 `mail()` 自己收到的真实值旁边，而两者之间没有任何调和：`mail()` 拿到的仍是真实收件人与主题，额外头里带着调用方的那份，于是投递出的报文可能同时存在两个互相冲突的 `To:`，`Subject:` 同理。路由不受影响——信封取自 `mail()` 的参数——但收件人看到的报文可能点名一个发件人本不打算显示的地址，主题也可能双显或被拼接。触发条件：`withTo(...)`/`withSubject(...)` 与 `withHeaders(['To' => …])` 或 `['Subject' => …]` 同时使用。SMTP 驱动则干净覆盖，因此两个驱动在此不一致——README 现已按驱动分别写明。

- 2026-10-01 · `coordinator — cross-module` · `new-evidence` — 修复建议，由协调人给出：选项由模块主选，而会改变「邮件投递到哪里」的选项归用户裁定。

  **先更正本条立案时的机制描述。** 我写的是「路由不受影响」，而这只在 MTA 不从头部取收件人时成立。PHP 把报文交给 `sendmail_path`（默认值是 `sendmail -t -i`），而 `-t` 让 MTA 从 `To:`/`Cc:`/`Bcc:` 里读收件人——这正是「第四个参数里出现 `To:` 行」成为经典收件人注入向量的原因，也是 Suhosin 专门有一档用来剥掉 additional headers 里的 To/Cc/Bcc 的原因。因此在标准的 Unix 配置下，第二个 `To:` 可以真的多出一个收件人，而不只是多一行可见文本。选择之前请对照部署自己的 MTA 实测：Windows 中继、或未带 `-t` 调用的 `sendmail`，结果可能不同。

  **（A）响亮地拒绝这种组合。** 在 `send()` 里、`deliver()` 之前，按大小写不敏感判定——头名不分大小写，而那个循环是原样存下名字的——当 `$mail->headers` 带 `To` 或 `Subject` 时抛 `MailException`，例如 *自定义 To/Subject 头不受 NativeMailer 支持；请用 withTo()/withSubject()*。约五行代码加两个用例（`withHeaders(['To' => …])`、`['Subject' => …]` 各自抛错；第三个自定义头照常透传）。除了本就自相矛盾的输入，行为不变，也不会有一封邮件改投别处，并且模块只保留一条点名收件人的路。README：写明原生驱动是拒绝它们，而不是追加上去。

  **（B）让自定义头生效。** 在 `send()` 里把 `To`/`Subject` 从 `$mail->headers` 取出、作为 `$to`/`$subject` 交给 `deliver()`，并在头部循环里跳过它们，使报文只写一行；`Subject` 走 `encodeSubject()`，自定义 `To` 走本模块其他所有地址都要过的同一道 `filter_var` 校验——否则模块就多了一条不经校验直达信封的路。约十行代码加四个用例。这是本轮之前 README 承诺过的行为，也让两个驱动在这两个名字上一致——代价是一次真实的行为变更：今天按 `withTo()` 投递的邮件，会改为投给自定义头里的地址。

  **（C）剥掉该头、保留 `mail()` 的参数。** 两行代码，但静默丢弃调用方写下的东西；与本模块「响亮失败」的取向相悖，不建议。

  **（D）保留已文档化的边界，把本条按 `deferred` 关闭。** 不改代码；重复的那一行仍在，而在带 `-t` 的 MTA 上多出来的收件人也仍在。

  建议：**（A）**。`withTo()` 与 `withSubject()` 本来就在，走头这条路等于把同一件事说两遍；拒绝它即可消除歧义，且永远不会改变邮件投到哪里。（B）只在项目希望「头说了算」时才更好，而那样必须补上地址校验，并在 README 写明自定义 `To` 会改变投递目标。无论选哪条，SMTP 驱动的 `To`/`Cc` 都要一并给出答案——见 `P2-5`。
