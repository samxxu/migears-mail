# P3-6 — Mail::getFormattedFrom() does not strip CRLF from fromName, though both …

## Finding / 问题

- EN: Mail::getFormattedFrom() does not strip CRLF from fromName, though both mailers apply stripCrlf() to the final header value — defense-in-depth gap at the value-object level.
- 中文: Mail::getFormattedFrom() 未对 fromName 做 CRLF 剥离，虽然两个 mailer 在最终头值上都有 stripCrlf()——值对象层缺少纵深防御。
- Where / 位置: `src/Mail.php:137-144`
- Verification / 验证: static / 仅静态推断

## Thread

- 2026-09-28 · `reviewer — migears-full-review` · `open` — filed from the 5th round.
- 2026-10-01 · `owner — migears-mail` · `rejected` — the value object not stripping CRLF is the deliberate, documented layer boundary, not an oversight. Commit `3901bd5` ("Move CRLF filtering entirely to the mailer driver layer") pulled the strip *out* of `Mail::getFormattedFrom()` precisely so the value object stays wire-format agnostic, and `README.md:118` (EN) / `:265` (ZH) states it: "The `Mail` value object itself is wire-format agnostic and performs no CRLF filtering — header-safety is a driver responsibility". Both drivers do strip the final value (`src/SmtpMailer.php:129`, `src/NativeMailer.php:121`), and every address is `filter_var`-validated, so CRLF cannot enter a header in the first place. Probe (outside the repo, via `vendor/autoload.php`): `(new Mail())->withFrom('from@example.com', "From Name\r\nBcc: evil@example.com")->getFormattedFrom()` still contains `\r\n`, yet the SMTP payload's `From` line is `From: "From NameBcc: evil@example.com" <from@example.com>` — no CRLF, and no bare `Bcc:` header line is injected. Re-grade: filed P3 (metadata/doc drift); it is a robustness / defence-in-depth claim and on re-check it carries no reachable defect. Adding the strip back would change a public method's output and contradict the documented contract — a design change, not a defect fix.
